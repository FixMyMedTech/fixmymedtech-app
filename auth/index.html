    Authentication Guide¶

    This guide describes every authentication & account lifecycle flow in FixMyMedTech: self signup, email verification, login/logout, password reset, admin-invited users, admin portal access, and social (OAuth2) login.

    Stack: FastAPI + FastAPI-Users (auth core) · FastHTML (frontend) · Authlib (social login) · SQLAdmin (admin portal) · Postgres

    1. Identity model¶

    Accounts live in the local fixmymedtech.users table (Postgres). The core auth machinery is provided by FastAPI-Users 15 (backend/config/users.py), which we hide behind the app's own router (backend/routers/auth.py) so the browser-facing API contract stays stable.

    Key fields on users:

    Field Meaning
    email Unique login id (always stored lower-case)
    hashed_password bcrypt password hash (via pwdlib/BcryptHasher)
    is_active Disabled accounts can't log in
    is_verified Email verified (login does not enforce this)
    is_superuser Grants access to the /admin portal

    The 1:1 profile, default organization and membership are created alongside a new user by every provisioning path (signup, OAuth, admin invite).

    2. Tokens & sessions¶

    All tokens are JWTs signed with AUTH_JWT_SECRET (≥ 32 bytes, HS256).

    Login token¶

    Minted by the JWT auth backend (JWTStrategy, lifetime AUTH_TOKEN_TTL, default 7 days), payload {sub, exp}. It is a Bearer token: the frontend ships it to the backend as Authorization: Bearer <token>.

    Server-side session (frontend)¶

    The FastHTML frontend stores the login token server-side in an encrypted cookie session, never in localStorage:

    • /login POST → req.session["token"] = access_token
    • features/auth/helper.py → get_token(req), clear_session(req), require_auth() / require_auth_verified() (validates against /api/dashboard/stats and redirects to /login?expired=1 on 401)
    • /logout clears the session (the backend JWT is stateless)

    So the browser only ever holds the session cookie; the JWT never reaches it.

    Email tokens (verification / reset / invitation)¶

    These are signed with the same AUTH_JWT_SECRET but have a different payload shape and are consumed by FastAPI-Users' verify() / reset_password() UserManager methods:

    Token Claims aud TTL
    Login {sub, exp} fastapi-users:auth 7 d
    Verify email {sub, email, exp} fastapi-users:verify 1 h
    Reset password {sub, email, password_fgpt, exp} fastapi-users:reset 1 h

    password_fgpt is required. reset_password() verifies password_fgpt (a bcrypt hash of the user's current hashed_password) against that stored hash. Any hand-minted reset token missing this claim is rejected with HTTP 400 Reset failed:. Never build these tokens by hand — route them through UserManager.forgot_password() or reproduce the exact claim set described in §6.

    3. Self signup (public)¶

    browser → POST /api/auth/signup {email, password, full_name, organization_id?, ...}
  1. UserManager.create() hashes the password (bcrypt), is_verified=false
  2. Profile row created (id = user id, generated username)
  3. Organization resolved-or-created + OrgUser membership (role)
  4. on_after_register hook sends a WELCOME email + a VERIFICATION email

    Response is {message}. Duplicate email → HTTP 409 user_already_exists. The frontend /signup page renders distinct success / "account already exists" states.

    A self-registered user is is_verified=false but can log in immediately (login does not gate on verification).

    4. Email verification¶

    Triggered on self signup (on_after_register) or on demand via POST /api/auth/request-verification (anti-enumeration: always returns the same message).

    1. The hook calls UserManager.request_verify() → verification token {sub, email, aud: fastapi-users:verify} (1 h).
    2. send_verification_email() builds a backend link {API_BASE_URL}/api/auth/verify?token=... — note it points at FastAPI, because /api/auth/* is a backend route.
    3. user_manager.verify(token, request) checks signature + audience, that sub/email match the stored user, and sets is_verified = true.
    4. The router then 302s the browser to {FRONTEND_URL}/login?verified=1 (or ?verified=0 on failure), and the login page shows a corresponding alert.

    Template: backend/templates/email_verification.html.

    5. Login & logout¶

    Login¶

    POST /api/auth/login {email, password}
  • get_by_email (lower-cased)      → 404 user_not_found
  • verify_and_update(bcrypt)       → 401 invalid_credentials
  • hash-rotation (argon2→bcrypt)   → transparent upgrade
  • JWTStrategy.write_token(user)   → {access_token, user:{id, email}}

    The frontend /login POST stores the token in the session and redirects to /dashboard (or ?next=). Error mapping shown to the user: user_not_found / email_not_confirmed / invalid_credentials.

    Logout¶

    POST /api/auth/logout returns {message} — it is stateless; the frontend /logout route just clears the server-side session and redirects to /login.

    6. Password reset ("Forgot password")¶

    Public flow, fully functional since the reset-token fix:

    POST /api/auth/forgot-password {email}      (body: LoginRequest incl. password)
  → UserManager.forgot_password()
      token = {sub, password_fgpt = bcrypt(current hashed_password),
               aud: fastapi-users:reset}   (1 h)
  → on_after_forgot_password → send_reset_password_email()
      link = {FRONTEND_URL}/reset-password?token=...     (frontend page)
  → always returns the same message (no email-address disclosure)

    The invited user clicks the link → FastHTML /reset-password?token=...:

    GET  /reset-password?token=…   renders the form (redirects to /login if absent)
POST /reset-password {token, password, password2}
      validates: token present, len ≥ 8, passwords match
      → POST /api/auth/reset-password?token=…&password=…   (query params!)
          → UserManager.reset_password(token, password)
              verifies signature + aud + password_fgpt vs current hash
              400 Reset failed: … on bad/expired/single-use token
      success screen → "Go to login"

    Important details:

    • The backend endpoint declares token and password as query parameters, so the frontend API helper (_post) appends them to the URL and sends an empty JSON body.
    • Reset tokens are single-use and the fingerprint ties them to the exact current hash — changing the password invalidates any outstanding link.
    • Template: backend/templates/email_reset_password.html.

    7. Admin-invited user (invitation email)¶

    When a superuser creates a user in the SQLAdmin portal (/admin/user/create), UserAdmin provisions a fully-functional account and sends an invitation email — not a verification email:

    1. on_model_change normalizes/strips fields, forces is_verified=false, seeds a random password hash.
    2. after_model_change creates the Profile, a default Organization and an OrgUser (role admin).
    3. It mints a proper reset token (same shape as §6 {sub, email, password_fgpt, aud: fastapi-users:reset}, 1 h) and sends send_invitation_email() → backend/templates/email_invitation.html ("You've been invited to FixMyMedTech", button links to {FRONTEND_URL}/reset-password?token=...).
    4. The invited user sets their own password through the reset page and can then log in (login doesn't require verification).

    A mail failure is logged and never aborts user creation.

    Gotcha (fixed): the old tokens used aud: fastapi-users:reset-password and omitted password_fgpt, so every such link returned 400 Reset failed:. The invitation route must use aud: fastapi-users:reset and include the fingerprint claim to be accepted by reset_password().

    Admin-side email actions (backend/routers/admin_email.py, /admin-panel)¶

    Endpoint Purpose
    GET /admin-panel/invite Invitation form (full_name, email)
    POST /admin-panel/invite Find-or-create user, sends verification email
    POST /admin-panel/send-verification/{user_id} Resend verification link
    POST /admin-panel/send-reset/{user_id} Reset-password email (with password_fgpt)

    All require the admin session (require_superuser).

    8. Admin portal (/admin)¶

    The SQLAdmin UI at /admin is guarded by AdminAuth (backend/admin_auth.py):

    • Login is a form POST (username = email, password), validated with pwdlib against the stored bcrypt hash and is_active + is_superuser.
    • On success the session cookie stores admin_user_id (signed with AUTH_SESSION_SECRET).
    • Every request re-verifies that the id maps to an active superuser (authenticate()).
    • require_superuser() is the FastAPI dependency equivalent for the /admin-panel/* endpoints (HTTP 403 otherwise).

    Create a superuser with docker compose exec backend python scripts/create_superuser.py (or promote an existing user's is_superuser flag).

    9. Social login (OAuth2)¶

    Optional providers — Google, GitHub, Discord — registered in backend/config/oauth.py from *_CLIENT_ID / *_CLIENT_SECRET env vars (only when both are set).

    browser → GET /api/auth/oauth/{provider}            (frontend /login buttons)
  → Authlib redirects to the provider
provider → GET /api/auth/oauth/{provider}/callback
  1. exchange code for access token
  2. fetch userinfo (email + name)
  3. find-or-create LOCAL users row (upsert)
       • new user: hashed_password="!" (unusable), is_verified=true
       • profile + default org + admin membership created
  4. mint a LOCAL JWT (JWTStrategy) and redirect to
     {FRONTEND_URL}/oauth-callback?access_token=…
     (token passes through the URL for a single hop)
frontend → /oauth-callback stores token in the session → /dashboard

    Notes:

    • Discord only returns email when the identify email scopes apply and the account has a verified email; the code then falls back to discord-{id}@fixmymedtech.local (flagged so admins can fix it).
    • GitHub uses the user:email scope; profile name is name/preferred_username.
    • The OAuth user can later log in with !-hash accounts only through OAuth — use admin send-reset to give them a password if needed.

    12. Environment variables¶

    Variable Used for Default
    AUTH_JWT_SECRET Signs login / verify / reset JWTs (≥ 32 bytes) old 30-byte dev secret
    AUTH_TOKEN_TTL Login JWT lifetime (seconds) 604800 (7 d)
    AUTH_SESSION_SECRET Admin portal session cookie dev-admin-session-secret
    FRONTEND_URL Base for reset/invite links & OAuth callback http://localhost:8888
    API_BASE_URL Base for verify links (backend) http://localhost:8888
    PUBLIC_API_URL Overrides API_BASE_URL for verification links –
    LOGO_URL Branding in email templates Supabase asset URL
    MAIL_* SMTP (server/port/user/pass/from/starttls/tls) unset → console log
    GOOGLE_/GITHUB_/DISCORD_CLIENT_* OAuth provider creds unset → provider disabled

    13. Security notes¶

    • Emails are lower-cased on input, so User@X.org and user@x.org are the same account.
    • Forgot-password / verification-resend endpoints return a fixed message (no account enumeration).
    • Reset and verification tokens are short-lived (1 h) and signed with the app secret — rotation of AUTH_JWT_SECRET invalidates all outstanding links.
    • Session cookies are HttpOnly server-side sessions; the JWT never reaches the browser.
    • Admin portal and /admin-panel/* are restricted to active superusers.
    • AUTH_JWT_SECRET must be ≥ 32 bytes to avoid the InsecureKeyLengthWarning (generate with openssl rand -base64 48).

    Deployment Guide¶

    This guide walks through deploying FixMyMedTech from scratch: provisioning the server, configuring nginx, and setting up the GitHub Actions deployment workflows for both development and production environments.

    1. Architecture overview¶

                              ┌────────────────────────────────────────────┐
  browser / QR scan ─────▶│  nginx (host, :80/:443)                    │
                          │                                            │
                          │   prod.fixmymedtech.org ─▶ 127.0.0.1:5001  │  frontend (FastHTML)
                          │   dev.fixmymedtech.org  ─▶ 127.0.0.1:5002  │  frontend (FastHTML)
                          │   qr.fixmymedtech.org   ─▶ 301 ─▶ dev.fixmymedtech.org
                          │                                            │
                          └────────────────────────────────────────────┘
                                      │                │
                                      ▼                ▼
                              frontend container   backend container (FastAPI :8888)
                                      │                │
                                      └───── HTTP ─────┘
                                              │   │
                       Supabase Postgres ◀────┘   │   (DB only, fixmymedtech schema)
                                                  ▼
                                     minio container (internal minio:9000)
                                       volumes: minio-data (per environment)
    • The frontend (FastHTML) runs on port 5001 inside the container (fasthtml.serve() default) and talks to the backend over Docker's network.
    • The backend (FastAPI) runs on port 8888 inside the container.
    • The MinIO container serves every stored object (minio:9000 internally) and keeps its data in the named minio-data volume.
    • On the host, docker compose publishes the services only to 127.0.0.1, so nothing is exposed publicly except through nginx. MinIO is never exposed by nginx — the frontend proxies image routes (e.g. /profile/photo) to the backend, which reads MinIO on the internal network.
    Env App dir Compose file Frontend (host) Backend (host) MinIO (host)
    Prod /opt/fixmymedtech docker-compose.yml 127.0.0.1:5001 127.0.0.1:8888 127.0.0.1:9000/9001
    Dev /opt/fixmymedtech-dev docker-compose.dev.yml 127.0.0.1:5002 127.0.0.1:8889 127.0.0.1:9002/9003

    MinIO on a shared server. Each environment runs its own MinIO container and its own minio-data volume, so dev and prod never share objects. Both backends reach MinIO as minio:9000 on their internal compose network; only the host-published ports differ (prod 9000/9001, dev 9002/9003) — they must stay different when both stacks run on the same host, otherwise the second one fails to bind its ports. The bucket name defaults to fixmymedtech (override with MINIO_BUCKET), scoped to each stack's own MinIO. Set MINIO_ROOT_USER / MINIO_ROOT_PASSWORD once, before any upload (see Troubleshooting).

    2. DNS records¶

    Create A records pointing all three subdomains to your server IP (one record per hostname):

    Hostname Type Value
    prod.fixmymedtech.org A
    dev.fixmymedtech.org A
    qr.fixmymedtech.org A

    naming Note: nginx cannot redirect qr → dev if DNS does not resolve the domain to the server. Verify with dig qr.fixmymedtech.org.

    3. Server setup (one time)¶

    Tested on Ubuntu 22.04 (arm64).

    sudo apt update && sudo apt upgrade -y

# Docker + compose plugin
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER

# nginx + certbot
sudo apt install -y nginx certbot python3-certbot-nginx

# (optional) firewall — allow only SSH, 80, 443
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable

# app directories used by the deploy workflows
sudo mkdir -p /opt/fixmymedtech /opt/fixmymedtech-dev

    Log out and back in so the docker group takes effect, then confirm: docker run --rm hello-world.

    4. nginx setup¶

    The nginx config lives in the repo at infrastructure/nginx/nginx.conf and is not deployed automatically — copy it manually:

    sudo cp infrastructure/nginx/nginx.conf /etc/nginx/sites-available/fixmymedtech
sudo ln -s /etc/nginx/sites-available/fixmymedtech /etc/nginx/sites-enabled/fixmymedtech

    The file contains four server blocks:

    1. prod.fixmymedtech.org → proxy to 127.0.0.1:5001 (SSL).
    2. qr.fixmymedtech.org on :80 → 301 https://dev.fixmymedtech.org$request_uri.
    3. qr.fixmymedtech.org on :443 (SSL) → same 301 redirect.
    4. dev.fixmymedtech.org → proxy to 127.0.0.1:5002 (SSL), plus Certbot's :80 → :443 redirect block.

    Important — conflicting server names. If you previously had a qr block in /etc/nginx/sites-available/default (or another file), nginx loads the first one it finds and ignores the rest, so the redirect silently stops working. Remove the duplicate qr.fixmymedtech.org server blocks from default, keeping only the ones in fixmymedtech:

    sudo grep -rn "qr.fixmymedtech.org" /etc/nginx/
# then edit /etc/nginx/sites-available/default and delete the qr blocks
sudo nginx -t

    Issue certificates (must match the ssl_certificate paths in the config):

    sudo certbot certonly --nginx -d prod.fixmymedtech.org
sudo certbot certonly --nginx -d dev.fixmymedtech.org
sudo certbot certonly --nginx -d qr.fixmymedtech.org

    Check and reload:

    sudo nginx -t          # expect NO "conflicting server name" warnings
sudo systemctl reload nginx

    5. Supabase projects¶

    Create two projects (one for dev, one for prod) at https://supabase.com.

    Only PostgreSQL is used from Supabase:

    • Authentication runs against our own fixmymedtech.users table (FastAPI-Users + JWTs signed with AUTH_JWT_SECRET) — no Supabase Auth or GoTrue dependency.
    • File storage (avatars, device photos, documents) runs on MinIO, not Supabase Storage.

    Setup:

    1. No manual schema step needed — the backend creates the fixmymedtech schema and applies every migration from infrastructure/migrations/*.sql at startup (tracked in fixmymedtech.schema_migrations).
    2. Project Settings → Database → Connection string → copy the URI (use the pooler for remote access, DATABASE_URL).

    6. GitHub Actions secrets¶

    In the repo Settings → Environments create two environments:

    • development — deployed from the dev branch.
    • production — deployed from the main branch.

    Add these secrets per environment (replace *_ with DEV_ or PROD_):

    Secret (required unless noted) Description
    *_DEPLOY_HOST / *_DEPLOY_USER SSH host and user
    *_DEPLOY_KEY SSH private key
    *_DEPLOY_PORT SSH port (defaults to 22 if unset)
    *_SUPABASE_DB_URI Postgres URI → DATABASE_URL
    *_FRONTEND_URL Public frontend URL, e.g. https://dev.fixmymedtech.org
    *_PUBLIC_API_URL Public backend URL — base for email verification links
    *_SESSION_SECRET Signs the frontend session cookies (random, e.g. openssl rand -hex 32)
    *_AUTH_JWT_SECRET Signs API JWTs (random long string)
    *_MINIO_ROOT_USER / *_MINIO_ROOT_PASSWORD MinIO admin credentials (shared by backend + minio container)
    *_MINIO_BUCKET (optional) Bucket name (default fixmymedtech)
    *_SUPERUSER_EMAIL / *_SUPERUSER_PASSWORD / *_SUPERUSER_NAME (optional) Auto-created admin on first deploy
    *_MAIL_SERVER / *_MAIL_PORT / *_MAIL_USERNAME / *_MAIL_PASSWORD / *_MAIL_FROM / *_MAIL_FROM_NAME (optional) SMTP — verification & password-reset emails
    *_GOOGLE_CLIENT_ID / *_GOOGLE_CLIENT_SECRET / *_GITHUB_* / *_DISCORD_* (optional) OAuth sign-in (disabled when absent)
    *_GEMINI_API_KEY / *_AUTO_PROCESS_PHOTO (optional) Photo white-background processing

    Notes:

    • AUTH_JWT_SECRET and SESSION_SECRET are different secrets — one signs JWTs in the backend, the other signs session cookies in the frontend. Never leave them at their dev defaults in production.
    • OAuth and GEMINI_API_KEY map to empty values when the secret is absent, so leaving them unset simply disables the feature (no .env corruption).

    Secrets are mapped by the workflows:

    • .github/workflows/deploy-dev.yml → DEV_* secrets, development env, app dir /opt/fixmymedtech-dev, uses docker-compose.dev.yml.
    • .github/workflows/deploy-prod.yml → PROD_* secrets, production env, app dir /opt/fixmymedtech, uses docker-compose.yml.

    7. What a deploy does¶

    Each workflow runs three steps on a GitHub runner:

    1. Write .env on the server (via SSH) — expands the secrets into /opt/fixmymedtech[-dev]/.env (used by docker compose). It contains the full set: DATABASE_URL, DB_SCHEMA, FRONTEND_URL, PUBLIC_API_URL, SESSION_SECRET, AUTH_JWT_SECRET, MINIO_* credentials + bucket, SUPERUSER_*, the SMTP MAIL_* block, and the optional OAuth / GEMINI_API_KEY entries. API_URL is fixed to http://backend:8888 (internal network).
    2. Copy the code (via scp) — backend, frontend, the compose file, and infrastructure (so migrations ship with the image).
    3. Build and deploy — docker compose up -d --build --remove-orphans. This also builds/starts the minio service; its minio-data volume survives redeploys, so previously uploaded objects are preserved.

    At container startup, the backend runs backend/migrations.py, which applies any pending SQL migrations from infrastructure/migrations/ before serving traffic.

    Superuser auto-creation: if SUPERUSER_EMAIL / SUPERUSER_PASSWORD are present in the server's .env, the backend also creates (or promotes) that admin right after migrations — no manual SSH step needed. The workflows already map these from DEV_SUPERUSER_* and PROD_SUPERUSER_* GitHub secrets (SUPERUSER_NAME sets the display name).

    Email links: verification emails are built from PUBLIC_API_URL (set it to the public URL where the API is reachable, e.g. https://dev.fixmymedtech.org), and password-reset links from FRONTEND_URL.

    8. Shipping a release¶

    • Dev: push to dev → auto-deploys to /opt/fixmymedtech-dev.
    • Prod: push to main → auto-deploys to /opt/fixmymedtech.
    • Manual: both workflows support workflow_dispatch — run them from the Actions tab.

    After a deploy, verify:

    # on the server, per environment
cd /opt/fixmymedtech[-dev]
docker compose ps
curl -s http://localhost:8888/health   # backend (prod 8888, dev 8889)
curl -sI https://dev.fixmymedtech.org  # or prod.fixmymedtech.org
curl -sI https://qr.fixmymedtech.org   # expect a 301 to dev

    9. Troubleshooting¶

    Symptom Fix
    conflicting server name "qr..." ignored Duplicate qr block in sites-available/default — remove it, keep only the one in fixmymedtech, nginx -t + reload.
    qr.fixmymedtech.org not redirecting DNS A record missing; or the listen 443; block lacks the ssl flag / options-ssl includes.
    Signup returns 400 Bad Request Check docker compose logs backend for the traceback; most often the email is already registered or the SMTP settings (MAIL_*) are missing/invalid.
    Migrations not applied docker compose logs backend | grep -i migration — migrations run on backend startup against DATABASE_URL.
    App up but browser shows cert warning Certbot cert does not cover the hostname — re-issue with certbot certonly --nginx -d <host>.
    Profile/device photo returns 404 The object is missing in MinIO. Verify the backend container can reach minio:9000 (docker compose logs backend | grep -i minio); if the minio-data volume was recreated (docker volume rm), all objects are gone — uploads must be redone.
    Uploads fail / AccessDenied on get MINIO_ROOT_USER/MINIO_ROOT_PASSWORD changed after data was written, or they differ between backend and the minio container. They must be identical in both services and stable — set them once before the first upload.
    Verification emails link to http://localhost:8888 PUBLIC_API_URL is empty — set it to the public backend URL and redeploy.
    Backend crashes at startup with invalid literal for int() with base 10 MAIL_PORT is empty — keep it numeric (the deploy workflow defaults it to 587).
